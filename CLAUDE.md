# Claude Code Project Instructions — SOUTHERN DIGITAL SURVEY

## Project Overview
Build a polished, responsive website for **SOUTHERN DIGITAL SURVEY**, a land surveying business in Aluva, Kerala.

Read `design.md` before implementing or changing UI. Treat it as the source of truth for colors, typography, spacing, components, motion, and visual direction.

## Tech Stack
- HTML
- CSS
- JavaScript
- Tailwind CSS

Use the project's existing setup and conventions. Do not introduce a framework, build system, or dependency unless necessary and justified. If Tailwind CSS is already configured, follow its installed version and configuration style.

## Working Rules
1. **Inspect before editing.** Review the existing folder structure, source files, assets, package configuration, and `design.md`.
2. **Follow the design system.** Reuse the defined tokens and consistent component styles. Do not invent new colors or fonts without a clear reason.
3. **Keep the website minimal.** Prioritize content hierarchy, whitespace, alignment, readability, and useful interactions over decoration.
4. **Make responsive layouts.** Test mobile, tablet, and desktop sizes. Prevent horizontal overflow.
5. **Use semantic HTML.** Prefer accessible native elements, logical heading order, meaningful button labels, and appropriate alt text.
6. **Keep JavaScript purposeful.** Use it for real interactions, not effects that can be handled cleanly with CSS or HTML.
7. **Keep performance in mind.** Optimize images, avoid unnecessary dependencies, and minimize layout shifts.
8. **Do not fabricate business information.** Never invent services, years of experience, qualifications, certifications, customer testimonials, project results, or statistics.
9. **Preserve existing work.** Do not rewrite unrelated files or remove existing features without a reason.
10. **Keep changes focused.** Make the smallest coherent change that achieves the requested result.

## Implementation Workflow
For each task:
1. Read relevant instructions and inspect the existing implementation.
2. Identify the files that need changing.
3. Make the requested changes without unrelated redesign.
4. Check responsive behavior and visual consistency.
5. Run available checks or build commands if configured.
6. Report briefly what changed, which files were affected, and any checks that could not be run.

## Code Quality
- Use clear, descriptive names.
- Avoid duplicated markup and styles when a small reusable component or utility would improve consistency.
- Remove dead code only when it is directly related to the change.
- Avoid unnecessary comments; add comments only when they clarify non-obvious behavior.
- Do not leave placeholder links or fake functionality presented as complete.
- Do not hardcode repeated design values when existing design tokens are available.

## Definition of Done
A change is complete when:
- It meets the user's request.
- It follows `design.md`.
- It works at mobile and desktop sizes.
- It does not introduce obvious console errors or broken interactions.
- Business claims and contact details are not fabricated.
- The implementation remains consistent with the existing project structure.
